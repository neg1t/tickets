# Оптимизация зала на 50 000 мест и внедрение WebGL — план реализации

> Для исполнителя: использовать `superpowers:executing-plans`. Выполнять этапы последовательно и отмечать чекбоксы только после проверки результата. Не делать push или remote PR без отдельного разрешения пользователя.

**Дата:** 27 октября 2026 года.  
**Статус:** реализация продолжается на ветке `codex/hall-50000-performance`; этап 2 реализован, этап 3 включает индексы покупателя и пространственные Canvas-блоки. Для этапа 4 созданы общая сцена, геометрия, hit testing, viewport, LOD и жесты; адаптер команд Konva к `RendererContract` остаётся открытым. Этап 5 частично реализован: WebGL2 рисует места instanced-проходом, частично обновляет стили, отсекает невидимые места и выводит подписи в отдельный Canvas-слой. Видимые индексы объединяются в упорядоченные диапазоны, тип символа передаётся как атрибут экземпляра; отдельные draw calls по типам не нужны. Этап 6 подключил WebGL к `SeatView` и редактору через `HallViewport`, сохранив Canvas выключенным по умолчанию; Canvas не готовит WebGL-сцену, пока движок не выбран; drag-preview передаёт временные позиции в GPU-буфер. Порядок слоёв, пиксель цвета места в светлой и тёмной палитрах, реальная потеря/восстановление контекста, fallback, освобождение ресурсов, resize и пауза в фоне проверены в Chromium на SwiftShader. Полная визуальная parity и проверка на физических мобильных устройствах остаются открытыми. Есть синтетические замеры 50k/100k на SwiftShader. Сравнение движков на 50k/100k и мобильные GPU-бюджеты остаются открытыми.
**Цель:** быстро открывать, просматривать и редактировать зал на 50 000 мест; обеспечить отзывчивую покупку билетов на телефонах.  
**Архитектура:** общая модель сцены и взаимодействий, загрузка геометрии по участкам, независимые обновления доступности. WebGL2 отрисовывает массовый слой мест; Canvas/Konva сохраняется как резервный рендерер и временный слой сложных объектов редактора.  
**Стек:** React, TypeScript, Effector, Nx, Vite, существующий Konva, WebGL2, Web Workers, IndexedDB; Vitest и Playwright для проверки.

Пути ниже относительно корня `tickets-frontend`. Новые файлы обозначены явно. Существующие изменения рабочей копии необходимо сохранить. Документ дополняет общую дорожную карту, не заменяя её.

## 2. Целевое поведение

- Покупатель сначала видит обзор секторов, цены и доступность; подробные места появляются при выборе сектора или приближении.
- Обзор готов до загрузки всей геометрии. Крупные сектора дополнительно делятся на пространственные блоки.
- Перемещение камеры и выбор одного места не запускают обработку 50 000 объектов.
- Доступность и цены обновляются отдельно от постоянной геометрии.
- Редактор открывает рабочую область до завершения фоновых диагностических проверок; публикация ждёт полной проверки актуальной ревизии.
- WebGL является обязательной частью реализации этого плана. Включение по умолчанию происходит после проверки корректности и мобильных бюджетов. Canvas остаётся рабочим резервным режимом.

**Приёмка:** первый интерактивный обзор не ждёт всех 50 000 мест; быстрое переключение не отображает старый сектор; большой сектор не нарушает ограничение детализации.

## 4. Команды проверки при реализации

Запускать из корня `tickets-frontend`. Для каждого этапа сначала запускать относящиеся к нему тесты; расширять проверки после интеграции. Этапы 1–3 уже проверялись выборочными unit-, build- и Playwright-прогонами; production-замеры выше остаются лабораторными наблюдениями с указанным размером выборки.

```powershell
pnpm exec nx run-many -t build -p domain,geometry,fixtures,renderer-konva,local-storage,seat-view,hall-editor
pnpm exec vitest run --project local-storage --project renderer-konva --project seat-view --project hall-editor --project fixtures --project studio
pnpm exec nx build studio
$env:HALL_PRODUCTION_PREVIEW = '1'
$env:HALL_BROWSER_MATRIX = '1'
pnpm exec playwright test --config apps/studio/playwright.config.mts apps/studio/e2e/performance-hall.spec.ts
Remove-Item Env:HALL_PRODUCTION_PREVIEW
Remove-Item Env:HALL_BROWSER_MATRIX
```

Ожидание: успешная сборка и проверки существующего поведения; baseline-тест до оптимизаций может нарушать вновь установленные бюджеты и должен сохранять отчёт с фактическими числами. Не увеличивать таймаут как способ «исправить» производительность.

После создания новых библиотек и тестов:

```powershell
pnpm exec nx run-many -t build -p renderer-core,renderer-webgl,hall-viewer
pnpm exec vitest run --project renderer-core --project renderer-webgl
pnpm exec nx run-many -t typecheck,lint -p renderer-core,renderer-webgl,hall-viewer,renderer-konva,seat-view,hall-editor,studio,embed
pnpm exec nx run-many -t build -p studio,embed
$env:HALL_PRODUCTION_PREVIEW = '1'
$env:HALL_BROWSER_MATRIX = '1'
pnpm exec playwright test --config apps/studio/playwright.config.mts
pnpm exec playwright test --config apps/embed/playwright.config.mts
Remove-Item Env:HALL_PRODUCTION_PREVIEW
Remove-Item Env:HALL_BROWSER_MATRIX
```

Имена новых Nx/Vitest-проектов при регистрации должны совпадать с командами. Для embed переменные production-preview/matrix начинают действовать после этапа 8. Реальные GPU-проверки выполнять в браузере: jsdom и моки WebGL не доказывают корректность изображения. Если тестовый хост использует software renderer, помечать результаты и не считать их мобильным GPU-бенчмарком.

## 5. Порядок и ограничения

1. Этап 1 — измерения.
2. Этапы 2–3 — устранение лишней работы и повторные измерения.
3. Этапы 4–6 — общий контракт, WebGL, подключение покупателя и редактора, fallback.
4. Этапы 7–8 — загрузка по участкам и полноценный лёгкий покупатель.
5. Этап 9 — фоновые проверки и частичные изменения редактора.
6. Этап 10 — интеграционная приёмка и постепенное включение.

WebGL ускоряет отрисовку, но не устраняет чтение каталога, повторный parse и ненужные вычисления. Worker переносит работу с главного потока, но не делает передачу данных бесплатной. Кеши должны иметь пределы, а частичная загрузка — сохранять выбор, корректность наличия билетов и версию схемы.

Размер блоков, точный DPR, предел GPU/Canvas-памяти, допустимое количество draw calls и сроки этапов фиксировать по результатам baseline и прототипа. Не обещать конкретное кратное ускорение до измерений.

## 6. Проверенные технические источники

- [Konva: performance tips](https://konvajs.org/docs/performance/All_Performance_Tips.html) — сокращение рисования, число слоёв, кеширование и pixel ratio.
- [MDN: WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices) — batching, ресурсы и ограничения устройств.
- [MDN: drawArraysInstanced](https://developer.mozilla.org/en-US/docs/Web/API/WebGL2RenderingContext/drawArraysInstanced) — отрисовка экземпляров общей геометрии.
- [MDN: webglcontextlost](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextlost_event) и [webglcontextrestored](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/webglcontextrestored_event) — жизненный цикл контекста и восстановление ресурсов.
- [web.dev: INP](https://web.dev/articles/inp) — оценка отзывчивости и порог 200 мс на 75-м процентиле.

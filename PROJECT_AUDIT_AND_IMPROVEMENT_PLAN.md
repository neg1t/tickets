## 1. Экспертная оценка

Проект имеет хорошую основу для специализированного редактора. Здесь уже есть самостоятельная модель зала, сохранение идентификаторов мест, команды с undo/redo, разделение доступности и геометрии, пространственные индексы, уровни детализации, PDF-подложки, локальное восстановление и значительное количество тестов. Полная перепись не обоснована.

Главная проблема — **не цена рисования одного кресла**, а стоимость смены состояния и отсутствие общего цикла отрисовки. При drag редактор способен отказаться от пакетной отрисовки всей видимой области. После изменения документа синхронно выполняются общие проверки и перестроение индексов. В WebGL-режиме камера проходит через несколько React-компонентов и эффектов, а слои рисуются независимо.

Как внутренний инструмент приложение уже полезно. Как готовый SDK для чужого продукта оно требует стабилизации: завершённого embed, контракта сессии/ревизии, документации, управления размерами и устойчивых публичных типов. Визуально это рабочий технический интерфейс; до качества SeatLayer больше всего не хватает иерархии действий, понятных состояний холста и качественных схем-примеров.

| Область | Оценка текущего состояния | Практическое следствие |
|---|---|---|
| Домен и геометрия | Хорошая основа | Сохранить схемы, стабильные ID и отдельные математические функции |
| Рендеринг | Оптимизации есть, интеграция незавершена | Исправлять горячие пути и синхронизацию до расширения WebGL |
| Компоненты | Публичные props полезны; ответственности смешаны | Разделить управление, состояние документа и UI без смены внешнего поведения |
| Производительность 50k | Pan Canvas в проверенном обзоре плавный; редактирование имеет задержки | Измерять drag, commit, генерацию и обновление доступности отдельно |
| Проверки качества | Браузерные сценарии в основном работают, общий gate красный | Сначала восстановить достоверный lint/typecheck/test |
| UX/UI | Оболочка уже отделена от каталога, но перегружена | Сократить постоянные панели и сделать контекстные действия |
| Встраивание | React-компоненты есть; embed — заглушка | Отдельная фаза подготовки SDK и примеров интеграции |

## 2. Что действительно проверено

### Окружение и границы

- Windows, AMD Ryzen 9 5900X, 24 логических потока; Chromium `156.0.8078.4`, headless, DPR 1.
- Desktop: 1440×1000; существующий стенд сравнения задаёт контейнер 1280 px. Mobile: 390×844, дополнительно штатный touch-тест mobile Chromium.
- Обычный Studio проверен в development и в собранном production preview на `http://localhost:4300/`.
- WebGL принудительно включён через существующие `rendererComparisonHarness.ts` и `hallViewportHarness.ts`.
- GPU в этой сессии: **ANGLE / SwiftShader**, программный рендеринг. Замеры не характеризуют реальную видеокарту пользователя.
- Проверены каталог, открытие редактора, pan, zoom, drag одного места, покупательская схема, адаптация к мобильной ширине, потеря WebGL-контекста и публичный SeatLayer Designer.
- Не подтверждены: скорость на физическом телефоне, работа аппаратного GPU, производственный backend, конкурентные продажи и полное соответствие WCAG. Эмуляция мобильного viewport не заменяет физическое устройство.

### Важное уточнение о WebGL

**Обычные страницы текущего Studio используют Canvas.** `HallEditor` и `SeatView` имеют `webglEnabled = false`; `EditorPage.tsx` и `BuyerPage.tsx` не передают разрешающий флаг. `selectRendererEngine('auto', false)` выбирает Canvas.

Это проверено в браузере: `data-seat-renderer="canvas"`. Подёргивания принудительно включённого WebGL реальны, но нельзя автоматически относить к нему все задержки обычного редактора. В следующих отчётах всегда записывать фактический движок, ревизию, режим сборки и GPU.

## 3. Подтверждённые проблемы и причины

Приоритеты: **P0** — восстановление достоверности проверок; **P1** — непосредственно ломает взаимодействие или создаёт заметные задержки; **P2** — качество продукта и интеграции; **P3** — расширение после стабилизации.

### F01 · P1 · Камера проходит через несколько независимых циклов

**Источники:** `libs/renderer-konva/src/lib/HallViewer.tsx:340`, `libs/hall-viewer/src/lib/HallViewport.tsx:143`, `libs/renderer-webgl/src/lib/WebGLHallCanvas.tsx:145`, `libs/renderer-webgl/src/lib/WebGLHallRenderer.ts`, `scheduleFrame`.

Цепочка: pointer → rAF pan → state `HallViewer` → effect `onViewportChange` → state `HallViewport` → effect `WebGLHallCanvas` → собственный rAF WebGL. Konva и Canvas подписей обновляются по другим путям. Добавление `memo` вокруг компонентов не создаст общий кадр.

**Последствие:** места, контуры, ручки и подписи могут двигаться в разные моменты. Это относится и к редактору, и к покупательскому `HallViewport`.

**Направление:** один контроллер камеры и один планировщик кадра для всех поверхностей. React получает редкие снимки для UI; высокочастотное движение не должно обходить дерево через эффекты. Принудительный синхронный draw допустим только внутри согласованного планировщика, с отключением дублирующего автопланирования соответствующих слоёв.

### F02 · P1 · При drag отключаются batches всех видимых мест

**Источник:** `libs/renderer-konva/src/lib/HallViewer.tsx:676`, ветка `sceneObjectNodes` около строки 1191.

Условие `movingKeys.size > 0` возвращает `null` для `dotBatches`. После этого все видимые места становятся отдельными `ObjectRenderer`. Подтверждён рост 12 → 2 636 узлов при движении одного места.

**Направление:** сохранять неподвижные batches. Выделить перемещаемые объекты в отдельный preview-слой, исключая их только из затронутых блоков. Для больших групп применять временную матрицу группы; не создавать React-элемент для каждого неподвижного кресла.

### F03 · P1 · Изменение одного места инвалидирует полную сцену

**Источники:** `HallViewer.tsx`, memo с зависимостью от `snapshot`; `HallViewport.tsx:203`, эффект с зависимостью от `snapshot.seats`; `WebGLHallRenderer.ts`, `setScene`.

Konva заново строит `buildHallScene` после смены snapshot. WebGL при новой ссылке `seats` сбрасывает prepared/ready scene, временно возвращается к Canvas, откладывает подготовку на два rAF, затем загружает новую сцену. `setScene` пересоздаёт массивы, индекс и буферы.

**Последствие:** локальное изменение способно вызвать работу, пропорциональную всему этажу, и переключение рендерера после отпускания мыши. Два rAF откладывают вычисление, но не делают его фоновым и не уменьшают объём.

**Направление:** явные ревизии геометрии и change set, обновление только изменённых элементов и блоков; полная установка сцены для открытия документа/массовой замены. Worker вводить после устранения повторных вычислений.

### F04 · P1 · Общие команды и диагностика блокируют UI

**Источники:** `libs/hall-editor/src/lib/editorCommands.ts:86,235,338,356`; `libs/hall-editor/src/lib/HallEditor.tsx:155`; `libs/hall-editor/src/lib/validation/validateLayout.ts`.

В обычном `applyPatches` каждый patch отдельно ищет и пересоздаёт массив коллекции. Это даёт порядка **O(P×N)** для P изменений в N местах, затем snapshot проверяется отдельно и ещё раз внутри draft. Специальный путь `applyLocalMove` уже улучшен; его наличие не ускоряет остальные команды. После смены draft `validateLayout` синхронно проверяет весь документ. Коллизии мест уже используют сетку; возвращаться к попарной проверке всех мест нельзя.

**Направление:** группировать patches по коллекции, проходить каждую коллекцию один раз, сохранять неизменённые ссылки. Локальные команды проверять локально; полную проверку выполнять на границе импорта/публикации и в фоновой диагностике с привязкой к ревизии. Проверка публикации остаётся обязательной.

### F05 · P1 · Потеря контекста оставляет первый WebGL-слой без мест

**Источник:** `libs/hall-viewer/src/lib/HallViewport.tsx:177`.

На первой потере контекста увеличивается счётчик; Canvas включается только после второй. Проверка через `WEBGL_lose_context` оставила `isContextLost() = true`, `data-seat-renderer="external"`, Canvas-узлов мест — 0 до явного восстановления. Автоматическое восстановление не гарантировано немедленно.

**Направление:** на первой потере показывать работоспособный Canvas; восстановление WebGL выполнять отдельно и переключаться после подтверждённого draw актуальной сцены. Ограничить повторы; не терять selection, камеру и незавершённое действие.

### F06 · P1 · Подписи не используют временные позиции drag

**Источники:** `WebGLHallCanvas.tsx:77,142,155`, `libs/renderer-webgl/src/lib/seatLabels.ts`.

GPU получает `previewPositions`, а `drawSeatLabels` читает исходную `scene` и не получает preview. Зависимости эффекта подписей также не содержат preview. Это установленное расхождение кода; отдельная пиксельная проверка движущейся подписи в этом аудите не проводилась.

**Направление:** единый resolved transform для символа, подписи, selection и hit test; проверка на zoom, где подписи видны.

### F07 · P2 · «Вписать» ограничен произвольным минимальным масштабом

**Источник:** `libs/renderer-core/src/lib/viewport.ts:6,45`.

`fitViewport` ограничивает scale снизу значением 0,1. Для геометрии большого размера требуемый fit меньше этого значения, поэтому весь этаж не помещается. Большой fixture открывается на нижнем пределе. Кроме того, проценты 1524%/1680% в маленьких схемах означают мировую единицу, а не понятный пользователю размер.

**Направление:** вычислять допустимый минимум относительно размеров документа и viewport, определить единицы и понятный базовый масштаб. Проверить первый wheel после fit: текущая формула тоже применяет фиксированный clamp. В редакторе отдельно определить политику камеры при смене этажей: `selectFloor` меняет сцену, но не передаёт новый `fitKey`, тогда как покупатель это делает.

### F08 · P2 · Обновление доступности всё ещё обрабатывает весь зал

**Источники:** `libs/seat-view/src/lib/SeatView.tsx:345,355`; `HallViewport.tsx`, `effectiveSeatUpdates`.

При новой ссылке `availability.seats` заново создаются карты цветов и массив обновлений всех мест; затем создаётся ещё один массив с цветами. GPU умеет частичные записи, но до него изменения приходят после полных CPU-проходов. Это проблема масштаба при частых live-обновлениях; её стоимость в реальном серверном потоке пока не измерена.

**Направление:** сохранить начальный snapshot и передавать изменённые ID/статусы отдельно, с номером ревизии и правилами переподключения. Не пересобирать геометрию при изменении доступности или цены.

### F09 · P0 · Проверки не дают достоверного зелёного состояния

Кроме реальных ошибок типов/границ, есть хрупкие тесты строк HTML. Performance-тесты полезны, но сравнение рендереров не имеет обязательного frame budget и не проверяет положения слоёв во время движения. Выборка 180 rAF при 45 шагах жеста может включать значительную долю покоя.

**Направление:** исправить gate без широких eslint-disable и ослабления бюджета; проверять поведение через доступные роли, а геометрию — через относительные инварианты. Производительность считать по реальному интервалу жеста. 50k на трёх этажах и 50k одновременно на одном этаже — отдельные fixtures.

## 4. Архитектура и пригодность компонентов

### Что сохранять

- `HallEditor`: controlled `value/onChange`, callbacks сохранения/публикации, `readonly`, locale и выбор движка уже образуют полезную точку интеграции.
- `SeatView`: отдельные layout, availability, prices, selection и `onBuyClick` позволяют оставить checkout у приложения-хоста.
- `domain`/`geometry`: Zod, branded coordinates, стабильные ID и проверка связей; не заменять их небезопасными casts ради скорости.
- Командную историю: это уже patches, а не полная копия документа на каждый шаг; ограничение истории уже существует.
- Доступный список порциями по 80 мест, защиту клавиш при вводе текста, abort PDF-import, локальное восстановление, WebGL resource lifecycle.

### Что мешает развитию

1. **Слишком много ответственности в одном компоненте.** `HallEditor.tsx` — 1982 строки, `HallViewer.tsx` — 1864, `SeatView.tsx` — 765, `dashboard.model.ts` — 1199. Размер сам по себе не ошибка; здесь он отражает смешение жестов, команд, загрузки, UI и вычислений.
2. **Renderer-independent слой зависит от Konva.** `HallViewportProps` наследуется от `HallViewerProps`, `HallTarget` экспортируется из `renderer-konva`; editor и buyer знают эту библиотеку. `renderer-core` при этом помечен как UI widget, что противоречит его роли и правилам Nx.
3. **Публичная поверхность не оформлена как SDK.** Пакеты private, React задан в dependencies конкретной версией; host-контракт peer dependencies и диапазон поддержки не определены. Это риск для внешней сборки, а не доказанный duplicate-React баг текущего монорепо.
4. **Нет готового embed.** `apps/embed/src/pages/embed/ui/EmbedPage.tsx` выводит «Пока нет данных для отображения». Нужны init/update/destroy, события, resize и обработка ошибок, а не только сборка пустой страницы.
5. **Нет отдельного руководства для потребителя.** README описывает демо. Нужны минимальные рабочие примеры, импорт CSS/темы, стоимость смены props, асинхронные callbacks, смена документа и правила ревизий.

Предлагаемые границы ответственности:

```text
domain + geometry
        ↓
renderer-core: camera, gestures, scene, targets, changes
        ↓                         ↓
renderer-konva              renderer-webgl
        ↘                         ↙
           hall-viewer: composition
             ↓               ↓
       hall-editor         seat-view
             ↘               ↙
             studio / host / embed
```

`renderer-core` не импортирует React, Konva или DOM-компоненты. Контроллер предоставляет снимок камеры и подписку для адаптеров; конкретные методы draw/resize остаются у рендереров. Внешний host не обязан знать выбранный рендерер.

## 5. Визуальный аудит и сравнение с SeatLayer

### Что проверено у референса

Открыт [SeatLayer Grand Theatre Designer](https://app.seatlayer.io/demo/designer/grand-theatre). Runtime показал `window.Konva.version = 10.3.0`, один stage и 7 слоёв. Следовательно, наблюдение о Konva подтверждено **для этого Designer**. Это не доказательство одинакового устройства всех покупательских/3D-режимов.

На [публичной странице демо](https://app.seatlayer.io/demo) доступны разные схемы и отдельные входы Designer/Buyer. Из визуально проверенного полезны: большая область холста, контекстный правый инспектор, компактные инструменты, сводка проверок, категории с числами и ценами, различимый stage и сектора. Производительность из маркетинга не использована как результат нашего сравнения.

Документация Konva рекомендует разделять статические и изменяемые слои, отключать лишний hit graph, использовать culling и кешировать по результатам измерений: [официальные рекомендации](https://konvajs.org/docs/performance/All_Performance_Tips.html). Многие из этих приёмов в проекте уже есть; повторное добавление общих «оптимизаций Konva» не устранит F01–F04.

### Недостатки текущего интерфейса

- Верхние панели повторяют название зала и служебные действия. `Изменений через onChange` находится в продуктовой оболочке; пользователю важнее статус сохранения и возможность отменить действие.
- Слева постоянно видны этажи, загрузка PDF и калибровка даже при обычном редактировании мест. При этом «Структура» не даёт полноценного дерева поиска/выделения объектов.
- 14 инструментов обозначены Unicode-глифами разной формы и веса. Title-подсказки есть, но визуально сложно различать схожие операции.
- Фон и контуры схемы почти одинаковы по контрасту, кресла детализированы раньше, чем появляется полезная пространственная иерархия. В маленьком примере нет очевидного ориентира сцены и подписей рядов на обзоре.
- Каталог рисует условную миниатюру из количества мест и зон, а не реальную схему. Пользователь не узнаёт свой зал по превью.
- В buyer одновременно используются цвета доступности и отдельные текстовые ценовые категории, однако на карте доступные места визуально одинаковы. Ценовая навигация слабая.
- На мобильном экране toolbar требует горизонтального просмотра, список/фильтры идут ниже карты, fixed-корзина отнимает заметную высоту. Общей горизонтальной прокрутки документа на 390 px нет, но это ещё не делает сценарий удобным.

### Рекомендуемое направление

**Редактор:** один верхний command bar: назад, имя, статус, undo/redo, preview, publish. Экспорт, версии и обслуживание — в меню. Слева компактные группы инструментов и открываемое дерево объектов; справа только свойства текущего выделения. PDF/калибровка — контекст импорта. Space временно включает pan, H/V сохраняются. Единые SVG-иконки, типографика и состояния фокуса.

**Холст:** на обзоре показывать сцену, сектора, проходы, вместимость и ценовую структуру; затем ряды; затем места и номера. LOD переключать по экранному размеру, с гистерезисом. Hover, selected, unavailable и validation должны отличаться не только цветом. Подписи сохраняют читаемый экранный размер и не перекрывают друг друга.

**Покупатель:** выбор сектора с понятной ценой, затем места; подробности выбранного места рядом с картой. На телефоне — карта с компактными zoom/fit и нижняя панель с выбором/итогом, раскрываемыми деталями и safe-area. Доступный список остаётся полноценной альтернативой карте.

**Каталог:** настоящая миниатюра опубликованной или сохранённой ревизии, отличимые состояния draft/published/recovery. Генерировать превью при сохранении/публикации, не строить живые canvas всех карточек.

Чтобы превзойти референс, выбрать узкий измеримый сценарий: например, «редактор зала 50k, перемещение сектора и массовая нумерация без зависаний; удобный мобильный выбор соседних мест». Добавление 3D или AI до стабилизации этих сценариев увеличит объём, но не решит текущую проблему.

## 6. Выбор подхода

| Вариант | Преимущество | Цена и риск | Решение |
|---|---|---|---|
| Стабилизировать существующий гибрид | Сохраняет возможности, данные и тесты | Требует дисциплины общего кадра и изменений сцены | **Рекомендуется** |
| Сделать основной слой полностью Canvas/Konva | Проще модель поверхностей; текущий обзор уже быстрый | Нужно доказать плотный 50k и высокую детализацию | Сохранить как fallback и контрольный вариант |
| Сразу переписать всё на WebGL | Единый GPU-проход потенциально масштабируется | Придётся восстановить текст, PDF, handles, доступность и множество сценариев | Сейчас не обосновано |

Решение о включении WebGL по умолчанию принять после приёмки корректности и измерений на аппаратном GPU. При желании продолжать WebGL-развитие нет необходимости сначала переписывать всю модель редактора.

## 7. Целевые критерии

Ниже — **предлагаемые цели**, а не уже достигнутые результаты. Перед работой зафиксировать конкретные desktop GPU и физический телефон, версию браузера, DPR, режим питания, fixture и сеть. Если исходная машина не выдерживает цель, обсуждать профиль поддержки, а не скрыто ослаблять проверки.

| Критерий | Предлагаемая приёмка |
|---|---|
| Камера всех слоёв | Одна ревизия камеры на frame; визуальное отклонение символа/подписи/overlay ≤1 CSS px |
| Desktop pan/zoom на 50k одного этажа | p95 интервала активных кадров ≤20 мс; p99 ≤33,4 мс на выбранном GPU |
| Mobile pan/zoom | p95 ≤33,4 мс на согласованном физическом устройстве |
| Одиночный drag | Начало preview ≤50 мс; неподвижные места сохраняют batches; один commit на отпускание |
| Обычный commit | Одиночное локальное изменение ≤50 мс на desktop-профиле; UI не ждёт полной диагностики |
| Изменение 1000 мест | Цель ≤150 мс синхронной работы; при превышении разбить подготовку, показать выполнение |
| Live availability | Обновление одного места не перестраивает геометрию и все GPU-буферы |
| Повторное открытие 50k | p75 ≤1 с на принятом desktop-профиле; cold-open и сеть измеряются отдельно |
| Отказ WebGL | Рабочий fallback после первой потери; камера/selection сохранены |
| Длительная сессия | 20 циклов открыть/закрыть и смены движка без роста числа живых stage/listeners; heap сравнивается после одинакового GC-процесса |

## 9. Порядок и ориентировочный объём

Оценка для одного опытного frontend-разработчика с доступом к тестовым GPU/телефонам. Это диапазон планирования, а не обещание срока; после задач 1–2 уточнить по измерениям и текущей ветке.

| Этап | Задачи | Оценка |
|---|---|---|
| Достоверная база | 1–2 | 2–4 рабочих дня |
| Исправление взаимодействий | 3–4 | 4–7 дней |
| Локальные обновления и проверки | 5–6 | 5–9 дней |
| WebGL parity, fallback, fit, inventory | 7–8 | 4–7 дней |
| Границы компонентов и UX | 9–11 | 7–12 дней |
| SDK/embed и интеграционная приёмка | 12 | 3–5 дней |

Итого ориентировочно **25–44 рабочих дня** для всего плана. Первую полезную поставку делать после задач 1–4: она должна убрать конкретные дефекты движения, а не ждать полного редизайна. Параллельная работа над UI возможна после фиксации жестов и контрактов, но требует отдельной координации.

Пока не включать в обязательный объём: 3D, AI-генерацию схем, совместное редактирование и полную замену рендерера. Профилированный Worker/подгрузка блоков нужны там, где после задач 3–6 остаётся измеренная проблема, а не как универсальное средство ускорения.

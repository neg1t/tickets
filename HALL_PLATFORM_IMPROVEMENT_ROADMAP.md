# Hall Platform — аудит и дорожная карта улучшений

**Дата:** 23 октября 2026 года.  
**База аудита:** `c35cde5` — Initial Hall Platform implementation through demo booking.  
**Статус:** предлагаемый план; реализация улучшений ещё не начата.  
**Цель:** превратить работающее локальное демо в удобный редактор залов и современный покупательский интерфейс, затем продолжить исходные Phase 09–13.  
**Архитектура:** сохранить React, TypeScript, Effector, Konva и независимые компоненты с props/callbacks. Разделить сохранённый документ, временное состояние жеста и представление; общие дизайн-токены использовать в DOM и Canvas.  
**Стек интерфейса:** Tailwind CSS для DOM, общие UI-компоненты, векторные символы мебели в Konva.

> Инструкция для продолжения: выполнять этапы последовательно, отмечать чекбоксы только после проверки критериев. Для реализации использовать `executing-plans` либо `subagent-driven-development`, если выбран режим работы с агентами. Не выполнять весь документ одним большим изменением. Не делать push или remote PR без отдельного разрешения пользователя. Этот документ разрешено хранить в репозитории по прямому запросу пользователя; исходная дорожная карта не заменяется.

## 1. Основной вывод и границы аудита

Реализован фундамент и сквозное локальное демо, **но не весь основной продукт и не законченная визуальная составляющая**. В исходной карте нумерация начинается с Phase 00: код соответствует работам до Phase 08 включительно. Далее уже предусмотрены API, SDK, embed/Flutter, performance/QA и production. При этом внутри первых фаз остаются функциональные и UX-пробелы, которые следует закрыть до стабилизации публичного SDK.

Проверены основные потоки и реализация всех существующих библиотек: domain, geometry, renderer-konva, hall-editor, pdf, local-storage, seat-view, fixtures; приложения studio и embed; конфигурация workspace, тестов и CI. Изучены схемы, генераторы, операции редактора, публикация, импорт, локальная покупка и тестовые сценарии. Выполнен визуальный осмотр работающего Studio на localhost. Внешние референсы изучены по публичным страницам возможностей и документации; закрытые редакторы конкурентов не проходили полноценное usability-тестирование.

Это инженерный аудит обнаруженных дефектов и рисков, а не гарантия нахождения всех ошибок или полный security pentest. Ниже отдельно обозначены подтверждённые кодом проблемы, риски для воспроизведения и ещё не реализованные требования. Отсутствие серверной авторизации у автономного демо само по себе не является уязвимостью.

### Что уже стоит сохранить

- Чистые геометрические функции, генераторы рядов/столов, пространственный индекс и reconciliation идентификаторов.
- Zod-проверки структуры, уникальности ID и связей между этажами, зонами, рядами и местами.
- Историю команд с undo/redo; ограничение истории в 100 команд уже существует.
- Разделение черновиков и опубликованных снимков; сохранение публикаций после удаления черновика предусмотрено тестами.
- Проверку revision при сохранении и публикации; это уже защищает от перезаписи устаревшей вкладкой.
- Транзакционное изменение локальных holds/orders в IndexedDB: нельзя утверждать, что здесь вообще нет защиты от конкурентного бронирования.
- Controlled selection, отдельные экземпляры моделей редактора/viewer, локальный PDF worker и отсутствие HTTP внутри универсальных компонентов.
- Unit/component/E2E-тесты и существующий CI. Их нужно расширить, а не создавать с нуля.

### Фактические проверки

- `pnpm nx run-many -t lint typecheck test build --all`: Nx сообщил **40 задач, 40 succeeded, 0 cache hits**.
- Дополнительная попытка `test-ci` оказалась неприменима без Nx Cloud: это ограничение конфигурации, не провал unit-тестов.
- Первый E2E-запуск с `CI=true` не стартовал: порт 4200 уже занят запущенным Studio, а reuseExistingServer в CI выключен. Существующий сервер не останавливался; повторный запуск выполнен в локальном режиме с переиспользованием сервера. Итог записан в разделе 10.
- Успешные текущие тесты не проверяют качество дизайна, непрерывность drag и полноту исходного продуктового замысла.

### Нереализованный продуктовый объём — не выдавать за готовые фазы

- UI создания/редактирования этажей; сцена, входы/выходы, подписи, препятствия, проходы и полигональные зоны как полноценные сущности. Сейчас переключение готовых этажей есть, authoring API/commands для этажей отсутствует.
- В доменной зоне нет явного типа GA и capacity; демо считает пустую зону GA на 20 человек. Пустой сектор и свободное размещение должны различаться.
- Нет authoring параметров рядов/столов, прямого редактирования кривых за handles, копирования, выравнивания, snapping, box selection.
- Нет пользовательской панели проверки коллизий, дублей видимых номеров, пустых рядов и ошибок размещения перед публикацией. Наличие geometry collision helpers не означает их интеграции.
- `apps/embed/src/pages/embed/ui/EmbedPage.tsx` — заглушка. React SDK, API adapter и WebView bridge — следующие исходные фазы, не регрессия.
- Нет измеренной работы на 10k–50k, visual regression suite и полного браузерного/mobile/a11y покрытия. CI уже есть, но E2E-конфигурация сейчас только Chromium.

## 3. Направление UI/UX

### Референсы и граница заимствования

Из [seats.io](https://www.seats.io/features) берём разделение Designer/seat picking, работу с секторами и этажами, быстрый переход от обзора к месту и различимые состояния. Из [SeatLayer](https://seatlayer.io/features/) — контекстные инструменты автора, проверки до публикации, опубликованную ревизию как основу покупательской схемы и удобный mobile picker. Это ориентиры взаимодействия; собственная визуальная система не должна копировать чужой бренд.

Под SeatLayer в этом документе принят `seatlayer.io`. Поиск также показывает отдельный `seat-layer.com`; эти продукты не смешиваются. При необходимости конкретный пользовательский референс можно уточнить на этапе макетов.

Три варианта развития:

1. Только перекрасить текущую страницу и переписать CSS на utilities — быстро, но сохраняет перегрузку и дефекты жестов; не рекомендуется.
2. **Рекомендуется:** сохранить ядро, поэтапно заменить оболочку, модель взаимодействия и мебельные символы. Проверяемость и совместимость данных сохраняются.
3. Полная замена редактора/рендерера — максимальный риск потерять текущие возможности; без результатов performance-профилирования не обоснована.

### Новый Studio

- Каталог как отдельный экран: карточка с миниатюрой, названием, количеством мест, датой изменения, статусом черновика/публикации. Поиск, сортировка и одно главное действие «Создать зал».
- Редактор занимает доступную высоту окна. Верхняя панель: назад, редактируемое имя, статус записи, undo/redo, preview, publish. Каталог и демо-администрирование не отнимают место у холста.
- Слева компактная полоса инструментов; раскрываемая структура «Этаж → сектор → ряд/стол → место», поиск объектов, visibility/lock.
- Справа контекстный инспектор шириной ориентировочно 280–320px: свойства выделения, единицы, inline errors. При multiselect — общие значения и явное «разные значения».
- Холст: спокойный фон, необязательная сетка, различимые границы секторов, сцена как ориентир; плавающие zoom/fit, подсказка активного инструмента и клавиш.
- Инструмент создания показывает preview до commit. Esc отменяет действие; Space временно включает pan; Delete, Ctrl/Cmd+Z, Shift+Z, copy/paste/duplicate не срабатывают при вводе текста.
- На узком экране панели превращаются в drawers. Покупательский экран проектируется mobile-first; для редактора на телефоне отдельно определить поддерживаемые операции, не обещать desktop CAD на 360px.

### Визуальный язык

Светлая нейтральная основа, один акцент, читаемая типографика 13–16px, иерархия primary/secondary/destructive, интервалы по общей шкале, умеренные радиусы и тени только для приподнятых элементов. Единые иконки, tooltip с названием/shortcut, понятные empty/loading/error/success состояния. Dark theme оставить расширением токенов, не блокировать ей первый релиз.

**Кресло:** сиденье, заметная спинка, подлокотники. **Стул:** сиденье и более тонкая спинка. **Место коляски:** отдельное пространство с обозначением доступности, а не кресло с другой заливкой. **Стол:** поверхность с номером и стулья вокруг, ориентированные к столу. Геометрия собственная векторная, пригодная для разных масштабов; не фотографии мебели.

На близком масштабе видны силуэт/номер, на среднем — упрощённое кресло, на общем плане — плотность/сектора. Круг допустим только как осознанная дальняя LOD-аппроксимация. Доступность и цена — разные визуальные каналы; selected обозначается контуром/галочкой, unavailable — дополнительным паттерном. Нельзя кодировать смысл только цветом.

### Покупательский экран

- Схема — основной элемент; цена/категория/доступность видны в tooltip на desktop и карточке/bottom sheet на touch.
- Идентификация: этаж, сектор, ряд, место; одного номера «1» недостаточно для повторяющихся рядов.
- Корзина закреплена справа на desktop и снизу на mobile: состав, итог, удаление, явная кнопка продолжения.
- Фильтры по цене/категории/доступности; текстовая клавиатурная альтернатива Canvas с поиском и ограниченным набором результатов, а не тысячи кнопок сразу.
- Обновление availability не убирает выбранные места молча: показать конфликт и предложить замену. Hold timer и expiry принадлежат host/session, не геометрии.
- Цель a11y: видимый focus, логичный tab order, восстановление focus после dialog, labels/status announcements, управление без мыши. Целевой touch target 44px для DOM-кнопок; на плотной карте — zoom и расширенные hit regions без неоднозначного выбора соседей.

## 4. Tailwind: миграция без потери переносимости SDK

Tailwind генерирует CSS, поэтому технически «полностью отказаться от CSS» нельзя. Цель — заменить ручные компонентные таблицы стилей на utilities и общие компоненты; оставить небольшой входной CSS для theme/fonts/base и редких специальных правил.

- Использовать актуальную совместимую Tailwind v4 через официальный [Vite plugin](https://tailwindcss.com/docs/installation/using-vite); точные версии зафиксировать в lockfile при реализации.
- Добавить `libs/ui` для Button, IconButton, Field, Select, Tooltip, Dialog, Drawer, Menu, Toast и `libs/design-tokens` для семантических токенов DOM/Canvas. Не превращать UI-библиотеку в зависимость domain/geometry.
- В Nx явно охватить исходники общих библиотек при [поиске классов](https://tailwindcss.com/docs/detecting-classes-in-source-files). Динамические статусы отображать через статические карты классов, не через строковую сборку имён.
- [Preflight](https://tailwindcss.com/docs/preflight) не должен глобально сбрасывать стили host-приложения. Для SDK выпускать отдельный scoped stylesheet с prefix/namespace; проверить portals и CSS variables. Потребитель SDK не должен устанавливать Tailwind или сканировать исходники пакета.
- Canvas не стилизуется Tailwind-классами: цвета/размеры/типографика приходят из общего token adapter и параметров symbols.
- Порядок переноса: tokens/primitives → каталог/оболочка → панели редактора → viewer controls → buyer. Старые CSS удалять после миграции конкретного потребителя и визуальной проверки, не одной массовой заменой.
- Проверка: production builds Studio/embed и отдельный host без Tailwind, два виджета с разными themes, отсутствие глобальных изменений button/input/body, отсутствие пропавших utilities.

## 5. Контракт взаимодействия и данных

### Drag transaction

`idle → pressed → dragging → commit | cancel`. В pressed сохраняются pointerId, исходные world-координаты, нормализованный selection, версия документа и viewport. До порога движения это click. Во время drag отображается временный transform на движущейся группе/overlay; базовый документ, история и внешнее onChange не обновляются на каждый пиксель. Preview включает связанные места, контур выделения и snap guides.

При pointerup выполняется одна атомарная команда и один onChange. При Escape/pointercancel/потере захвата/замене документа preview сбрасывается. Нулевой delta не создаёт историю. Выход за границу Canvas не равен mouseup; определить auto-pan у края. Если pan/zoom во время drag разрешён, вычислять delta в world space с актуальным преобразованием, не просто делить итоговую screen delta на новый scale.

**Приёмка:** объект движется до отпускания; offset grab point сохранён; выделение parent+child не удваивает перенос; undo/redo атомарны; click после drag не создаёт/выбирает лишний объект; readonly не мутирует документ. Проверить мышь, touch, pen, разные zoom, уход курсора за границы, cancel и внешнюю замену value.

### Схема v2

Добавить `schemaVersion` и миграцию v1 → v2 до введения новых полей. Сохранить существующие seatId и опубликованные снимки. Сначала протестировать импорт всех четырёх fixtures, PDF-документа и пользовательского v1 export; только потом менять формат записи.

Модель должна хранить тип/размеры/ориентацию места; параметры генерации ряда/стола, slot identity, ручные overrides; тип зоны и GA capacity; authoring этажей и декораций. Точная сериализация определяется в H02. Направление стула необходимо согласовать с tangent генератора: не считать произвольно, что tangent уже является направлением взгляда.

Публикация: структурная валидация → геометрические/продуктовые проверки → отчёт errors/warnings → неизменяемая версия. Ошибки блокируют publish; предупреждения имеют объяснение и явное решение пользователя. Изменение черновика не меняет уже привязанные к мероприятию места. Не обещать автоматическую проверку строительных/эвакуационных норм.

## 8. Как выполнять работу

Каждый этап разбивать на короткие изменения: воспроизведение → тест на поведение → реализация → targeted проверки → визуальная/интеграционная приёмка → фиксация результата в этой карте. Не писать тесты на буквальные Tailwind-классы или внутреннее число Canvas layers: проверять поведение, доступность и отображение.

Основные команды из корня workspace:

```powershell
pnpm nx run-many -t lint typecheck test build --all
pnpm nx e2e studio
pnpm nx e2e embed
```

Ожидание: все соответствующие targets завершаются успешно. Локально E2E может переиспользовать dev-server; в CI сервер должен стартовать из проверяемого commit на свободном порту. Для тестов библиотек выбрать обычный `test`; `test-ci` в текущем workspace требует Nx Cloud. Для каждой новой воспроизведённой ошибки сначала убедиться, что regression test падает по нужной причине, затем добиться PASS.

Архитектурные ограничения: domain не зависит от React/Konva/storage/API; geometry — чистая математика; renderer не знает о покупке; editor не ходит по HTTP; SeatView не подтверждает оплату. Глобальная Effector-модель допустима в единственном приложении Studio, но не в переиспользуемых экземплярах SDK.

## 9. Итоговая матрица приёмки

- [ ] Новый театр: этаж → сцена → сектор → несколько рядов с местами → нумерация → сохранение → публикация → выбор опубликованных мест.
- [ ] Банкет: круглый/прямоугольный стол со стульями; изменение количества, размера, поворота; стабильные retained seatId.
- [ ] Live drag: seat/row/table/zone/multiselect видимо движутся до отпускания; cancel/undo/redo корректны; один commit.
- [ ] Инспектор и handles дают одинаковую итоговую геометрию; места следуют за родителем.
- [ ] PDF: импорт, смена страницы, калибровка, поворот, редактирование, reload/export/import; нет сдвигов и бесконтрольного роста памяти.
- [ ] Data safety: reload с dirty, quota, повреждённый JSON, огромный PDF через JSON, смена зала во время import/save, две вкладки.
- [ ] Publication: изменение черновика и миграция не меняют опубликованную схему мероприятия; ошибки публикации объяснены.
- [ ] Buyer: mouse/keyboard/touch, мобильная корзина, обновление наличия, expiry/cancel/recover hold; malformed controlled inputs не доходят до checkout.
- [ ] UI: согласованные desktop/mobile макеты, узнаваемая мебель, читаемые labels, empty/loading/error состояния, RU/EN.
- [ ] Performance: 1k/10k/50k, culling, zoom/pan/group drag, длительная сессия, измеренный memory budget.
- [ ] SDK preparation: два виджета, host без Tailwind, отсутствие CSS leaks и HTTP в core, стабильные callbacks.

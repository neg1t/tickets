# Назначение ценовых сегментов местам и зонам — план реализации

> **Статус исполнения:** frontend-реализация P1–P8 выполнена и проверена в локальной ветке `feat/price`. По решению пользователя пункты, которым нужен backend, исключены из этой работы и остаются отложенными. Production-приёмка и любые remote Git changes не выполняются.

**Цель:** предоставить организатору отдельный экран, где он назначает полученные с backend ценовые сегменты отдельным местам, группам мест, зонам с местами и зонам свободного размещения.

**Архитектура:** независимый контролируемый React-компонент `PricingEditor` использует существующий `HallViewport` для отрисовки и выделения. Назначения хранятся отдельно от геометрии зала, в контексте мероприятия/сеанса и опубликованной версии схемы. Backend владеет каталогом сегментов и фактическими продажными ценами; host-приложение загружает и сохраняет данные.

**Стек:** существующие React, TypeScript, Effector, Zod, Nx, Konva/WebGL, Axios; IndexedDB для отдельного демонстрационного режима.

**Дата:** 28 октября 2026 года.

**Статус:** frontend-реализация P1–P8 завершена на локальной ветке `feat/price`; lint/typecheck/build, пакетные тесты и pricing E2E проходят. Demo flow дополнительно проверен в браузере, включая reload, buyer preview и неизменность котировки активного hold после смены цены. Pricing-специфичный CPU baseline на 50 000 мест записан для текущего состояния; сравнение до/после и проверка на согласованном мобильном устройстве остаются открытыми. Пользователь решил исключить пункты с backend из текущей работы; P0-согласование и проверка API на реальном сервере отложены. OpenAPI описывает предложенный контракт, а mock-проверки не доказывают production-интеграцию.

**Файл:** `PRICING_POLICY_FLOW_PLAN.md` в корне `tickets-frontend`.

## Chunk 1: Требования, поведение и модель данных

### 1. Подтверждённые требования

1. Ценовые сегменты создаются и редактируются во внешнем приложении: VIP, стандарт, эконом и другие.
2. В нашем приложении каталог приходит с backend. Здесь пользователь выбирает сегмент и назначает его объектам схемы.
3. Поддерживаются отдельное место, множество выделенных мест и зона с местами.
4. Поддерживаются зоны `kind: "ga"`: танцпол и другое свободное размещение с вместимостью и продажей по количеству билетов.
5. Для зоны с местами нужно учитывать и связи объектов, и геометрическое попадание мест в зону.
6. Выделение должно быть удобным для массовых операций: клики, добавление к выбору и рамка.
7. **Подтверждено пользователем: назначение сегмента зоне всегда заменяет сегмент у всех её мест, включая предыдущие ручные назначения.**
8. После назначения всей зоне разрешено снова выделить отдельные места и назначить им другой сегмент.
9. План описывает frontend flow и его контракты. Реализация backend и создание внешнего каталога в работу не входят; до backend-приёмки новые endpoints остаются контрактным предложением.

Термин «ценовая политика» в этом плане означает привязку к внешнему ценовому сегменту. Формулы динамического ценообразования, скидки, промокоды, возрастные тарифы и разные тарифы одного билета одновременно сюда не входят.

### 2. Проектные решения, принятые для плана

Эти решения предлагаются как исходные правила реализации; пользователь отдельно подтвердил только правило полной замены при назначении зоне.

| Вопрос | Решение для первой версии |
| --- | --- |
| Где действует назначение | В конкретном сеансе `occurrenceId` и его `layoutVersionId`. Один зал в двух сеансах может иметь разные цены |
| Что хранить | Стабильные `segmentId` по каждому месту и каждой GA-зоне |
| Как назначать всей seated-зоне | Развернуть выбор зоны в конкретные `seatId` и одной командой записать сегмент каждому |
| Есть ли наследование цены от seated-зоны | Нет. Текущий сегмент каждого места записан явно |
| Когда место попадает в геометрическую область | Его центр находится внутри области или на границе |
| Что делать с пересекающимися seated-зонами | Более поздняя явная операция заменяет сегмент общих мест |
| Можно ли сохранить неполное покрытие | Да. Отсутствие сегмента означает отсутствие продажной цены, а не бесплатный билет |
| Кто считает итог покупателя | Backend. Локальный расчёт нужен только для интерфейса и предпросмотра |
| Где сохранять цены | В отдельном ресурсе назначений; `HallLayoutDraft` и `LayoutSnapshot` остаются документами геометрии |

Если backend использует назначение на уровне мероприятия `eventId` сразу для нескольких сеансов, host обязан явно отобразить такой контекст в `occurrenceId` или согласовать изменение ресурса. Не распространять цены на другие сеансы неявно.

Важные ограничения существующего кода:

- `viewerMode: "edit"` включает геометрические сценарии; просто использовать его для ценового экрана недостаточно.
- Текущее рамочное выделение проверяет полное попадание bounds объекта и может возвращать ряды, столы и декорации. Для назначения нужны отдельные правила и фильтрация целей.
- При дальнем масштабе hit-test может исключать отдельные места. В режиме назначения выбор мест должен работать и на уровне отображения точками.
- Автоматически вычисленные renderer bounds зоны включают отступы. Их нельзя считать точной ценовой областью.
- `SeatView` использует продажный статус для окраски мест; окрашивание по сегментам на административном экране не должно менять доступность.
- Текущие `DemoHold` и `DemoOrder` не сохраняют деньги, а `BuyerPage` пересчитывает их суммы из актуальных prices. До разрешения редактирования демо-цен нужно добавить неизменяемые котировки, иначе старый заказ визуально изменит стоимость.
- В демо свободными считаются также некоторые зоны без явно связанных мест. Для нового flow это нужно заменить проверкой явного `kind === "ga"`.
- API-схемы используют `strictObject`. Новые поля в существующих ответах способны сломать старые клиенты, поэтому нельзя считать любое добавление поля автоматически совместимым.

### 4. Отдельный пользовательский flow

Последовательность:

1. Организатор выбирает мероприятие/сеанс и открывает действие «Назначить ценовые сегменты».
2. Host загружает опубликованную схему, каталог доступных для этого сеанса сегментов и сохранённые назначения.
3. Экран показывает зал, список сегментов, инструменты выделения и сводку покрытия.
4. Цель определяется автоматически: клик по креслу выбирает место, клик по свободной части сектора — сектор.
5. Обычный клик или рамка заменяет выбор; Ctrl+клик переключает отдельное место/сектор, повторный Ctrl+клик снимает его; Ctrl+рамка добавляет объекты.
6. Организатор выбирает сегмент и применяет его к выделенному; отдельная сводка «Перед применением» не показывается.
7. Операция меняет только локальный черновик; есть undo/redo.
8. Организатор проверяет результат и открывает покупательский предпросмотр при необходимости.
9. Нажатие «Сохранить назначения» отправляет черновик на backend одной атомарной записью.
10. После ответа host заменяет локальный документ серверным, обновляет baseline и сбрасывает dirty/history для сохранённой ревизии.

Локальное «Применить» и серверное «Сохранить» должны быть визуально различимы. До ответа backend черновик не считается действующей политикой продаж.

В демо добавить экран `pricing` в существующий `$mode` и действие у демо-мероприятия. Не внедрять новый router только ради этой функции. Для внешнего host можно использовать маршрут вида `/occurrences/:occurrenceId/pricing`, если router уже принадлежит этому host.

### 5. Компоновка экрана

- Верхняя панель: мероприятие/сеанс, версия схемы, статус сохранения, undo/redo, «Предпросмотр», «Сохранить назначения».
- Основная область: существующая схема зала, переключение этажей, pan/zoom.
- Каталог сегментов: имя, цвет, сумма и валюта из backend; поиск по имени; активный сегмент; состояние загрузки.
- Выбор с карты: прямой клик по креслу выбирает место с приоритетом над его сектором; клик по свободной части зоны выбирает сектор. Клик в пустое место карты очищает выбор.
- Ctrl+клик добавляет цель и переключает её при повторном клике. Обычный клик заменяет весь выбор одной целью. Обычная рамка заменяет выбор, Ctrl+рамка добавляет найденные цели.
- Undo/Redo остаются рядом с картой; список секторов продолжает выбирать сектор и фокусировать его на схеме.
- Сводка назначения: сегмент выбранных мест, состояние «Смешанные сегменты», число мест без назначения — остаются в покрытии и списке секторов без отдельного блока перед применением.
- Для seated-зоны: агрегированное состояние всех разрешённых мест. Если они отличаются, показывать «Смешанные сегменты», а не последнее назначение зоне.
- Для GA-зоны: сегмент и вместимость. Продажный остаток не выдавать за вместимость.
- Назначенные места окрашивать цветом сегмента. Выделение показывать дополнительной обводкой, сохраняя видимым сегмент.
- Места без назначения отображать нейтрально и помечать явно. Не полагаться только на цвет.
- Зоны окрашивать полупрозрачно; неподвижные подписи и маркеры не должны перехватывать выбор мест.
- Панели на узком экране сворачиваются, но «Применить» и число выбранных объектов остаются доступными.
- Каталог доступен только для чтения: нет кнопок создания сегмента, редактирования его суммы или вместимости зала.

### 6. Выделение без редактирования геометрии

Предлагаемый API viewer:

```tsx
<HallViewport
  snapshot={layout.snapshot}
  hallName={layout.hallName}
  zoneBounds={layout.zoneBounds}
  viewerMode="selection"
  selectableKinds={['seat', 'row', 'table', 'zone']}
  selectedTargets={selection}
  onSelectionChange={setSelection}
  seatAppearance={seatAppearance}
  zoneAppearance={zoneAppearance}
/>
```

Это проектируемые props: `selection`, `selectableKinds` и `zoneAppearance` ещё требуется реализовать.

Правила:

1. Клик по креслу выбирает место; если под курсором нет места, клик внутри зоны выбирает зону. Цель-кресло имеет приоритет над геометрией сектора.
2. Обычный клик заменяет выбор одной целью; Ctrl+клик добавляет цель, а повторный Ctrl+клик снимает её. Клик по пустому месту карты очищает выбор.
3. Рамка без модификатора заменяет выбор и выбирает места по попаданию центров, а сектора/ряды/столы — по полному попаданию bounds. Ctrl+рамка добавляет цели. Начать рамку можно поверх места; drag не превращается в перемещение геометрии.
4. Вычитание отдельным режимом убрано; повторный Ctrl+клик по выбранной цели снимает её.
5. Space + drag и средняя кнопка двигают камеру. Escape сначала отменяет текущий жест, затем очищает выбор.
6. На touch доступны явные инструменты выбора и навигации, pinch-zoom; появление второго указателя отменяет незавершённую рамку без изменения назначений.
7. Геометрические ручки, создание, удаление, поворот и перемещение объектов недоступны. Удаление ценового назначения — отдельное действие.
8. Выбор хранится отдельно от назначений, не отправляется на backend и сбрасывается при смене этажа, сеанса или версии схемы.
9. Действие «Выбрать места ряда/стола» разворачивает фактические дочерние места; ряд и стол не становятся самостоятельными объектами продажи.
10. Все разрешённые цели выбираются независимо от LOD и выбранного renderer. Результаты Canvas и WebGL должны совпадать.
11. Изменения режима selection не меняют старую семантику edit/view/pick. Новые фильтры одинаково применяются к точному hit-test, hit-test с допуском, hover и рамке.
12. Геометрические hidden/locked-состояния редактора не наследуются как запрет на ценовое назначение: нужны отдельные права этого flow.

### 7. Правила определения мест зоны

Для seated-зоны `Z` вычислить два набора на её этаже:

- **Связанные места:** `seat.zoneId === Z.id`; также места ряда/стола, у которого `zoneId === Z.id`.
- **Геометрические места:** центры мест внутри `Z.polygon`; если polygon отсутствует — внутри явно сохранённого `layout.zoneBounds[Z.id]`.

Итог — объединение этих наборов с удалением дублей.

Точности и ограничения:

- `polygon` имеет приоритет над прямоугольным `zoneBounds`. Сам bbox polygon нужен только для предварительного поиска.
- Если нет ни polygon, ни явных zoneBounds, использовать только связи и объяснять это в сводке.
- Не использовать автоматически расширенный bounds зоны из renderer как геометрическую область.
- Точка на границе входит в зону. Для вычислений с погрешностью определить один общий tolerance в world units, независимый от zoom; использовать одинаковый алгоритм в preview и применении.
- Использовать фактическую `seat.position` из опубликованного snapshot, как renderer. Не прибавлять `manual.offset` повторно.
- Касание зоны краем символа кресла при центре снаружи не включает место. Это выбранное для плана правило «пересечения».
- Места другого этажа исключаются даже при совпадающих координатах.
- Связанное место за геометрической границей включается и отображается в диагностике.
- Место с явным `zoneId` другой зоны, но центром внутри Z, также включается. Перед применением показать число таких пересечений.
- Назначение цены не переписывает `seat.zoneId`, связи с рядами/столами или polygon.
- При выборе нескольких зон для одного сегмента объединить `seatId`, применить команду один раз.
- Invalid polygon/bounds — явная диагностическая ошибка геометрического разрешения; не применять приблизительный bbox вместо некорректного polygon.
- Для больших залов: индекс по этажу → запрос bbox → точная проверка центра; не сканировать весь зал на каждом pointermove.

Пример: зона A содержит 20 связанных мест и ещё 3 геометрически попавших места без связи с A. После удаления дублей операция назначает сегмент всем 23 местам и объясняет расширение выбора.

### 8. GA-зоны и неоднозначные схемы

`kind === "ga"` — единственный признак свободного размещения. Пустая seated-зона автоматически танцполом не становится.

Назначение GA-зоне записывается по её `zoneId` и задаёт цену одного входного билета. При вместимости 500 продажа трёх билетов означает `quantity: 3`, не создание трёх фиктивных мест. Вместимость и текущий остаток при назначении не меняются.

Если в GA-зоне найдены связанные или геометрически попавшие сидячие места, вывести блокирующую диагностику для назначения этой зоне: данные нужно исправить в редакторе схемы или исключить ошибочную область. Не преобразовывать GA-зону в seated-зону автоматически и не назначать ей одновременно два вида инвентаря.

В первой версии одна GA-зона имеет один сегмент. Несколько тарифов/квот внутри одного танцпола требуют отдельной модели ticket offers и не эмулируются дублированием зоны или capacity.

### 9. Замена назначений и пересечения

| Действие | Результат |
| --- | --- |
| Назначить зоне A сегмент Standard | Каждое разрешённое место A получает Standard, включая прежние VIP/ручные назначения |
| Затем выделить два места A и назначить VIP | Только эти два места получают VIP; сводка зоны A становится смешанной |
| Снова назначить A сегмент Economy | Все её места, включая эти два, получают Economy |
| Назначить сегмент пересекающейся зоне B | Общие места получают сегмент B как результат новой явной операции |
| Очистить назначения зоны A | Удалить назначения у всех её мест, включая ручные |
| Очистить GA-зону | Удалить только её GA-привязку |
| Повторить назначение того же сегмента | Не создавать пустую запись undo/redo и не увеличивать dirty без изменений |

Правило «последняя операция» относится к последовательным действиям одного локального черновика. Конкурентные сохранения разных пользователей разрешаются через revision-конфликт, без скрытого last-write-wins.

Одна команда назначения или очистки нескольких целей — одна запись истории с обратимым diff. Undo восстанавливает все предыдущие назначения, в том числе ручные, заменённые назначением зоне.

### 10. Модель каталога и документа назначений

Проектируемые структуры:

```ts
type PricingSegment = Readonly<{
  id: string;
  name: string;
  color: string;
  status: 'active' | 'archived';
  price: Readonly<{ amountMinor: number; currency: string }>;
}>;

type PricingCatalog = Readonly<{
  occurrenceId: string;
  revision: number;
  items: readonly PricingSegment[];
}>;

type PricingAssignments = Readonly<{
  seatSegments: Readonly<Record<string, string>>;
  gaZoneSegments: Readonly<Record<string, string>>;
}>;

type PricingAssignmentDocument = Readonly<{
  schemaVersion: 1;
  occurrenceId: string;
  layoutVersionId: string;
  revision: number;
  catalogRevision: number;
  assignments: PricingAssignments;
}>;
```

- `segmentId` — ключ, имя — отображаемое значение. Совпадение имён не объединяет разные сегменты.
- Каталог приходит уже с ценой для данного сеанса. Если внешняя система разделяет категорию и тариф, адаптер должен вернуть согласованный стабильный ID продаваемого сегмента, а не вычислять цену на клиенте.
- `color` — валидируемый цвет, например `#RRGGBB`. Если backend цвета не выдаёт, host назначает стабильную палитру по ID; не принимает произвольный CSS.
- Денежные значения — целые minor units, безопасные для JSON number, с ISO-кодом валюты.
- В одном сеансе первая версия поддерживает одну валюту. Смешанный каталог требует фильтрации backend или блокирующей диагностики.
- Нулевая цена допустима только при явном активном сегменте с `amountMinor: 0`.
- Отсутствующий ключ означает «не назначено». Пустая строка, неизвестный ID и `null` не являются допустимыми назначениями.
- В canonical state нет `zoneDefaults` для seated-зон. Агрегаты и список геометрических попаданий вычисляются, а не сохраняются как ещё один источник истины.
- Нет копий сумм в каждой привязке, координат, платёжных токенов или цен в самом `Seat`.
- Архивный/исчезнувший сегмент сохраняется видимым как проблемное старое назначение, но его нельзя назначить новым целям. Сохранение с таким назначением блокируется до замены/очистки.
- Обновление каталога не должно незаметно менять показанную цену: показать изменения и потребовать повторного подтверждения перед сохранением.
- Для сеанса хранится одна актуальная карта назначений на текущую версию схемы; история backend может храниться отдельно.

Пример сохранённого документа после назначения зоне и двух индивидуальных изменений:

```json
{
  "schemaVersion": 1,
  "occurrenceId": "occ-001",
  "layoutVersionId": "layout-v7",
  "revision": 4,
  "catalogRevision": 12,
  "assignments": {
    "seatSegments": {
      "seat-a1": "segment-standard",
      "seat-a2": "segment-vip",
      "seat-a3": "segment-vip"
    },
    "gaZoneSegments": {
      "zone-dance": "segment-economy"
    }
  }
}
```

- Собственный `onChange` и следующий за ним controlled echo не должны восприниматься как внешняя загрузка и стирать undo.
- Любое несовпадение контекста `layout/value/catalog` блокирует применение до согласованной загрузки.

### 12. Предлагаемый контракт backend

Это предложение для backend-команды, а не описание существующих endpoints. В этом репозитории реализуются DTO, OpenAPI, TypeScript-клиент и host-интеграция; сервер, SQL и C# здесь не разрабатываются.

| Операция | Предлагаемый endpoint | Назначение |
| --- | --- | --- |
| Каталог сегментов сеанса | `GET /api/v1/occurrences/{id}/pricing-segments` | Read-only каталог с revision и ценами для контекста сеанса |
| Сохранённые назначения | `GET /api/v1/occurrences/{id}/pricing-assignments` | Документ назначений и его revision |
| Полная атомарная запись | `PUT /api/v1/occurrences/{id}/pricing-assignments` | Замена maps назначений по expected revision |
| Продажные цены | Существующий `GET /api/v1/occurrences/{id}/prices` | Backend возвращает итоговые деньги по seatId/GA zoneId |

Для схемы использовать уже согласованный endpoint опубликованного сеанса/версии. ID сеанса, версия схемы, назначение и каталог должны соответствовать одному контексту.

Пример каталога:

```json
{
  "apiVersion": "v1",
  "occurrenceId": "occ-001",
  "revision": 12,
  "items": [
    {
      "id": "segment-vip",
      "name": "VIP",
      "color": "#8B5CF6",
      "status": "active",
      "price": { "amountMinor": 500000, "currency": "RUB" }
    }
  ]
}
```

Ответ GET назначений: `{ "apiVersion": "v1", "document": <PricingAssignmentDocument> }`. Существующий сеанс без назначений возвращает пустые maps и `revision: 0`; отсутствие самого сеанса — 404.

PUT передаёт:

```json
{
  "apiVersion": "v1",
  "layoutVersionId": "layout-v7",
  "catalogRevision": 12,
  "assignments": {
    "seatSegments": { "seat-a1": "segment-vip" },
    "gaZoneSegments": { "zone-dance": "segment-economy" }
  }
}
```

Заголовки: `Authorization: Bearer ...`, `If-Match: "4"`, `Idempotency-Key: <operation-id>`.

Пример успешного ответа: envelope с `apiVersion`, новым `document` и `effectivePrices` в существующей структуре `ApiSeatPrices`. Внутри документа сервер увеличивает revision и возвращает принятый catalogRevision. Повтор запроса с тем же ключом и телом возвращает прежний результат, не выполняя замену повторно.

Условия backend:

1. Проверить tenant/права по токену, принадлежность сеанса и версии схемы.
2. Проверить ожидаемые revision документа и catalogRevision.
3. Проверить каждый target ID и active segment ID, допустимую валюту и принадлежность сегмента контексту.
4. Разрешать в `gaZoneSegments` только реальные GA-зоны; seat map — только реальные места этой версии.
5. Валидировать полное тело и применить его одной транзакцией. При любой ошибке ничего частично не сохранять.
6. Сохранить audit: actor из токена, время, context и изменённые target/segment ID.
7. Пересчитать или инвалидировать кеш итоговых продажных цен так, чтобы следующий GET не вернул старую карту под новой ревизией назначений.
8. Отсутствие цены никогда не трактовать как нулевую; hold для такой цели отвергать.
9. Не пересчитывать цены уже подтверждённых заказов. Предлагаемое правило для активных holds: сохранять их серверную котировку до истечения; backend должен подтвердить это до интеграции.
10. Ограничения размера PUT должны поддерживать полный целевой зал, включая 50 000 мест. При меньшем лимите согласовать отдельный атомарный batch-протокол, а не отправлять независимые частичные сохранения.

Не добавлять новые поля в существующие buyer-ответы без согласованного выпуска strict-схем и клиентов. Первая версия назначения может оставить `ApiSeatPrices` неизменным: `category` заполняется именем сегмента, а стабильные segment ID доступны через новый административный ресурс.

В контракт ошибок добавить согласованные коды `pricing_catalog_conflict`, `layout_version_conflict`, `invalid_pricing_assignment` и диагностику конкретных target ID. Для конкурентной записи использовать существующий `revision_conflict` и HTTP 409; точные статусы новых ошибок зафиксировать в OpenAPI.

Существующее расхождение `/api/v1/...` и описания другого C# API `/api/seating-configurations` нужно закрыть до подключения реального backend: либо принять эти маршруты, либо добавить явный адаптер клиента. Не смешивать DTO двух контрактов.

### 13. Сохранение, конфликты и восстановление

- Загружать каталог, схему и назначения с AbortSignal и проверкой request/context ID; поздний ответ предыдущего сеанса игнорировать.
- До согласованной загрузки всех трёх частей применение и сохранение недоступны.
- На сохранение зафиксировать точное тело, base revision и idempotency key; не менять их при повторе одной сетевой операции.
- Успех означает принятие полного серверного документа; не увеличивать revision оптимистично.
- Network error сохраняет черновик. Для неизвестного исхода операции предложить повтор с тем же ключом либо перечитать документ, не утверждая, что сервер ничего не записал.
- Пока исход PUT неизвестен, оставить изменение назначений заблокированным до повтора/перечитывания. Старый захваченный body не должен затем затереть новые локальные изменения. Recovery pending-операции сохраняет её key/body/base revision без auth-токена и восстанавливает это заблокированное состояние до разрешения исхода.
- При 409 не перезаписывать сервер молча и не удалять локальные изменения. Показать конфликт и действие загрузки серверной версии с явным подтверждением потери локального черновика.
- При обновившемся каталоге показать изменённые суммы/архивные сегменты; после принятия каталога повторно валидировать черновик.
- При 401/403 блокировать запись и передавать восстановление сессии host. Токены не сохранять в документе или локальном recovery.
- Смена сеанса, уход со страницы и перезагрузка предупреждают о dirty. Навигация не должна сохранять назначение без действия пользователя.
- В демо хранить документ отдельно от геометрии, ключом `occurrenceId + layoutVersionId`. Ошибка IndexedDB не должна изображаться успешным сохранением.
- Для демо назначения и вычисленные prices разместить в разных object stores одной базы `hall-platform-demo-booking`, чтобы сохранять их одной транзакцией. Отдельная база для назначений не обеспечит атомарность с текущими occurrences.
- Для recovery предусмотреть отдельную локальную копию с context, base revision, catalogRevision и updatedAt. Восстановление возможно только после проверки версии схемы и актуального server baseline; конфликты не применять автоматически.

Смена опубликованной схемы:

1. Ценовой flow не редактирует геометрию.
2. Сеанс привязан к неизменяемой опубликованной версии; изменённый редактором draft не влияет на открытые назначения.
3. Если backend сменил `layoutVersionId` сеанса, заблокировать сохранение старого документа и очистить текущий selection.
4. Перенос в новую версию — отдельное подтверждённое действие host/backend. Сохранять только совпавшие стабильные IDs после валидации, удалённые показать, новые оставить без назначения.
5. Пересечения зон на новой геометрии не запускают автоматическое переназначение. При необходимости пользователь повторно применяет сегмент зоне.

### 14. Связь с покупательской схемой и Flutter/WebView

Backend преобразует `seatId -> segmentId -> price` в `prices.seats`, а `gaZoneId -> segmentId -> price` — в `prices.zones`. Разворачивать seated-зону в места в момент покупки не требуется: результат уже материализован при назначении.

Предпросмотр в host использует тот же `SeatView`, но получает локально рассчитанную карту из черновика и активного каталога. Показывать явную отметку «Предпросмотр несохранённых назначений»; реальные hold/order запросы отключить. Деньги преобразовывать в UI через существующий mapper minor units, без хранения float в документе.

Настоящий покупатель, в том числе через Flutter WebView, получает цены только от backend. Административный документ и управление сегментами ему не передаются.

При сохранении назначений уже открытая покупательская страница не должна бесконечно показывать старые цены. Минимальная интеграция: перечитывать цены при возвращении на экран и перед созданием hold. Сам backend снова проверяет цену; если сумма hold отличается от показанной, host показывает серверную сумму и получает подтверждение покупателя до создания заказа. Подписки на изменения цен можно добавить позже, не делая их условием первой версии.

**Объём работ:** только frontend и локальное хранение в IndexedDB. Интеграция с backend, сетевые контракты и API-клиенты в этот план не входят.

## 2. Решения и границы реализации

### 2.1. Масштаб

Рекомендуемый вариант — относительные проценты: импортированная подложка отображается как **100%**, ползунок и числовое поле меняют её размер относительно сохранённого базового масштаба.

```text
relativePercent = 100 * scale / referenceScale
scale = referenceScale * relativePercent / 100
```

`scale` остаётся точным положительным числом; целыми показываются проценты. Для старых подложек один раз принять текущий scale за referenceScale: это сохраняет вид схемы и даёт понятные 100%. Базу обязательно сохранять, иначе после каждого открытия интерфейс будет сбрасываться на 100%.

Альтернативы: просто умножать scale на 100 всё ещё даёт дробные значения у больших PDF; округление самого scale до целого резко изменяет размеры. Обе не решают задачу.

Начальный диапазон ползунка — 10–400%, шаг 1%; точный ввод — положительные проценты с дробной частью. Выход точного значения за диапазон должен расширять диапазон, а не незаметно обрезать значение. Предусмотреть кнопки −/+, сброс к 100%, клавиатурное управление. Центр подложки при масштабировании фиксируется, включая повёрнутую подложку.

Главный сценарий — совместить места на PDF с местами редактора. В первый объём включить точную ручную подгонку и инструмент «Подогнать по двум точкам»: выбрать два центра мест на подложке и задать соответствующее расстояние в координатах схемы. Автоматическое распознавание мест по PDF не требуется. Существующая калибровка мира меняет `millimetersPerWorldUnit`; не использовать её как замену изменения размера подложки.

### 2.2. Локальные материалы и публичная схема

- В редакторе допустим составной `HallLayoutDraft` с подложками и PDF assets.
- В покупательской схеме и любом предпросмотре: `backgrounds: []`, без содержимого assets, без локальных ссылок на PDF/изображения. Поля пустых коллекций оставлять, если они обязательны по типам frontend-модели.
- Очистка не меняет исходный объект и не удаляет `decorations`, места, зоны, этажи или `zoneBounds`.
- PDF/изображения, параметры размещения, видимость, блокировка, opacity, pageNumber и referenceScale сохраняются в локальном контексте редактора.
- Ключ локального контекста включает тип владельца (`hall` или `occurrence`), его ID и подходящую версию/базу. Один `hallId` недостаточен для изоляции материалов зала и разных мероприятий.
- Покупательские схемы и предпросмотры не содержат подложек. Существующий пользовательский JSON-экспорт остаётся локальным резервным файлом редактора и сохраняет подложки вместе со схемой; он не отправляется на backend и не показывается покупателю.
- В другом браузере подложка отсутствует, поскольку она локальная. Это ожидаемое поведение; очищение данных браузера также удаляет её.

Не переписывать работающий локальный репозиторий целиком: использовать его Blob codec и транзакционные подходы. Отдельный локальный repository для материалов нужен для occurrence-контекстов; избежать двух конкурирующих источников правды для одной сессии.

### 2.3. Копия схемы мероприятия

В этом плане «конкретное мероприятие» трактуется как **occurrenceId**, поскольку это текущая единица назначения цен и продажи. Несколько сеансов одного event не должны автоматически получать одну изменённую схему. Если требуется общая схема для всех сеансов, это отдельное уточнение перед реализацией третьего блока.

Рекомендуется полный независимый snapshot, а не diff поверх зала: это позволяет свободно менять типы зон, этажи, ряды, столы и места без сложного слияния с будущими изменениями шаблона. Минус — дополнительный объём хранения; для текущей модели это проще и надёжнее patch-overlay.

При входе в редактор создавать рабочую копию в памяти. Только сохранение создаёт новую effective-версию мероприятия. Базовый зал и его опубликованные версии не изменяются. ID сохранившихся объектов сохраняются для переноса назначений; новые объекты получают новые ID. `snapshot.id`, `layoutVersionId` и ссылки на версию у этажей обновляются согласованно при фиксации.

В UI доступны все инструменты редактора; не передавать ограничения `publishedSeatIds` от базового зала. Геометрическая валидация остаётся: отсутствие ограничений редактирования не означает допустимость битых ссылок или отрицательной вместимости.

**Согласованность локальных demo-данных:** редактировать можно всё, но при применении копии нужно учитывать уже существующие локальные orders/holds и занятость GA-зон. При конфликте сохранять рабочий черновик и показывать конкретные несовместимые объекты, не удаляя demo-заказы молча. Проверки относятся только к существующей локальной модели; полноценный процесс переноса билетов не входит в эту задачу.
